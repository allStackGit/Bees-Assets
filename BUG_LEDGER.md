# Bug Ledger

Only defects validated by static code tracing are recorded here. No tests, builds, executables, benchmarks, simulations, or GitHub Actions were run.

### BUG-001 — Recurring movement refreshes can continuously invalidate live path searches and freeze gameplay
**Location:** `Scripts/Entities/Ships/Ship.Movement.cs`, `MoveToPoint()` / `HandleSupersededPathfindingRequest()` / `NearbyAsteroidDoubleCheck()`; `Scripts/Levels/Pathfinder.Search.cs`, `InvalidatePathRequest()` / `BTFindPath()`; recurring tracked-target callers in `Scripts/Levels/Commands/BombingRun.cs`, `Charge.cs`, `InAndOut.cs`, `SwipeSquad.cs`, `Heal.cs`, `FullRetreat.cs`, and `Scripts/Entities/Ships/Striker.cs`  
**Description:** Calling `MoveToPoint()` while a ship is already pathfinding marks the live request stale but does not cancel its `Task.Run` worker; the worker can continue searching until the five-second pathfinding time limit. When the stale result eventually completes, `HandleSupersededPathfindingRequest()` immediately starts a replacement search for the newest destination. Several recurring commands refresh moving ship targets unconditionally, and collision-asteroid avoidance similarly refreshed `FinalDestination` every second while an asteroid remained nearby. `BombingRun` is the worst tracked-target case because its timer can tighten to 0.25 seconds: any obstructed pursuit search taking longer than that is invalidated before it can be applied, while the abandoned worker continues consuming a path slot. With multiple moving ships this can keep all workers saturated with obsolete searches, continually queue replacements, prevent movement paths from settling, and consume enough CPU to make the game appear frozen. Recurring destination refreshes must let an active path search finish before issuing the next update.

### BUG-002 — Turret valid-target scans re-enumerate the range dictionary quadratically every physics tick
**Location:** `Scripts/Entities/Ships/Weapons/Turret.Targeting.cs`, `HasValidTarget()`; `Scripts/Entities/Ships/Weapons/Turret.Aiming.cs`, `Aim()`  
**Description:** An idle/non-firing turret calls `HasValidTarget()` from `FixedUpdate`/`Aim()`. `HasValidTarget()` stores `ShipsWithinRange.Values` as `IEnumerable<Ship>` and then calls LINQ `ElementAt(index)` for every index. `Dictionary<TKey,TValue>.ValueCollection` is not an indexable list, so each `ElementAt` walks the value enumerator again from the beginning. A scan that should be O(n) therefore performs O(n²) managed enumeration per turret per physics tick, in addition to the per-candidate obstacle linecasts. Dense battles with many turrets and many invalid/occluded candidates multiply this work across every turret and can produce severe main-thread stalls while ships are tracking targets.
