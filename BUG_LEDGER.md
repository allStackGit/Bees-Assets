# Bug Ledger

Only defects validated by static code tracing are recorded here. No tests, builds, executables, benchmarks, simulations, or GitHub Actions were run.

### BUG-001 — Recurring movement refreshes can continuously invalidate live path searches and freeze gameplay
**Location:** `Scripts/Entities/Ships/Ship.Movement.cs`, `MoveToPoint()` / `HandleSupersededPathfindingRequest()` / `NearbyAsteroidDoubleCheck()`; `Scripts/Levels/Pathfinder.Search.cs`, `InvalidatePathRequest()` / `BTFindPath()`; recurring movement callers in `Scripts/Levels/Commands/BombingRun.cs`, `Charge.cs`, `CircleSquad.cs`, `ClosestFriendly.cs`, `Guard.cs`, `InAndOut.cs`, `SwipeSquad.cs`, `Heal.cs`, `FullRetreat.cs`, and `Scripts/Entities/Ships/Striker.cs`  
**Description:** Calling `MoveToPoint()` while a ship is already pathfinding marks the live request stale but does not cancel its `Task.Run` worker; the worker can continue searching until the five-second pathfinding time limit. When the stale result eventually completes, `HandleSupersededPathfindingRequest()` immediately starts a replacement search for the newest destination. Several recurring commands refreshed moving ship/squad targets unconditionally, including Circle Squad's 0.25-second enemy-relative movement loop, while collision-asteroid avoidance refreshed `FinalDestination` every second. Fixed-destination command timers could also restate the exact same destination and invalidate a still-useful worker because `MoveToPoint()` performed invalidation before checking for duplicate work. `BombingRun` is another worst-case tracked-target path because its timer can tighten to 0.25 seconds. With multiple moving ships these loops can keep all path workers saturated with obsolete searches, prevent usable paths from settling, and consume enough CPU to make the game appear frozen. Periodic refreshes must let an active path search finish; identical in-flight destinations must be ignored rather than invalidated.

### BUG-002 — Turret valid-target scans re-enumerate the range dictionary quadratically every physics tick
**Location:** `Scripts/Entities/Ships/Weapons/Turret.Targeting.cs`, `HasValidTarget()`; `Scripts/Entities/Ships/Weapons/Turret.Aiming.cs`, `Aim()`  
**Description:** An idle/non-firing turret calls `HasValidTarget()` from `FixedUpdate`/`Aim()`. `HasValidTarget()` stores `ShipsWithinRange.Values` as `IEnumerable<Ship>` and then calls LINQ `ElementAt(index)` for every index. `Dictionary<TKey,TValue>.ValueCollection` is not an indexable list, so each `ElementAt` walks the value enumerator again from the beginning. A scan that should be O(n) therefore performs O(n²) managed enumeration per turret per physics tick, in addition to the per-candidate obstacle linecasts. Dense battles with many turrets and many invalid/occluded candidates multiply this work across every turret and can produce severe main-thread stalls while ships are tracking targets.

### BUG-003 — Long path workers spam main-thread logs every frame while a queue is waiting
**Location:** `Scripts/Levels/Pathfinder.cs`, `Update()`  
**Description:** `Pathfinder.Update()` iterates active worker slots whenever at least one path remains queued. For every active search whose stopwatch exceeds one second, it unconditionally calls `Debug.Log` on every subsequent frame until the worker finishes. Path searches are explicitly allowed to run for up to five seconds, so a four-worker backlog at 60 FPS can issue roughly 960 log calls during a single four-second interval after the one-second threshold, and continuous queued work can sustain the flood. Unity logging is performed from the main thread and is especially expensive in the Editor, so this diagnostic compounds the exact CPU/backlog condition that already makes pathfinding vulnerable to apparent freezes.
