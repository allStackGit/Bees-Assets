### BUG-001 — Failed setup/reconnect/strategy responses are dispatched into success-only payload handlers
**Location:** `Scripts/Server/SocketResponseLifecycleGuard.cs`, `ShouldKeepRequestPending()` / `FilterFailedResponses()`; `Scripts/Server/Socket.cs`, `Message()`, `HandleSetupLevelResponse()`, `HandleReconnectLevelResponse()`, `HandleMatchupResponse()`, `HandleStrategicCommandResponse()`; cross-repository BeesServer `security.js` authentication/authorization responses  
**Description:** BeesServer production authentication/authorization failures use a basic response containing the original request `Type`, `Hash`, and failure `Status` but omit the type-specific success payload. The lifecycle guard suppresses failed user-data/settings reads and failed basic writes, but not `setup-level`, `reconnect-level`, `get-matchup-strategy`, or `get-strategy`. Those failures therefore reach `Socket.Message()` and are dispatched by `Type` into handlers that assume success. A failed setup/reconnect is parsed with default `GameId = 0` and marks the Level setup/connected; a failed strategy response lacks `Name`/strategy fields and can fault or retire valid pending work. This is reachable during an initial setup authentication failure, reconnect ownership rejection, and during reconnect because ordinary standing-request resends resume as soon as the transport opens while BeesServer serializes reconnect/authentication separately from strategy requests. Non-success typed responses must be consumed before success handlers; retryable failures must leave their request standing, while terminal authorization failures must retire it without applying success state.
