# Bees development memory

This file records compact, reusable implementation knowledge that is expensive to rediscover. It is not a change log.

## Testing architecture

- Production runtime scripts still compile into Unity's predefined `Assembly-CSharp`. EditMode/PlayMode test assemblies cannot reference it directly, so existing tests intentionally use `Tests/*/RuntimeAssembly.cs` reflection adapters. Do not move production behind asmdefs merely to simplify a test unless that refactor is independently justified.
- Prefer EditMode for deterministic state/lifecycle tests and real-prefab tests that do not require a rendered frame. Use PlayMode for scene bootstrap, async worker completion, Unity destroyed-object semantics, frame progression, physics callbacks, rendering/GPU qualification, and long-running soak workloads.
- Authoritative command-line validation is the Unity Test Framework XML plus the exact executed-test count; Unity process exit/log noise alone is not sufficient.
- The release gate is `Tools/Run-BeesReleaseGate.ps1`; keep slow qualification categories opt-in so the correctness loop remains practical.
- Leave new Unity `.meta` generation to Unity; do not manually create `.meta` files during remote repository work.

## Campaign qualification

- `CampaignMissionCatalog` plus `LevelIntro` represent the current intended mission sequence: 0 Anomaly, 1 Reinforcements, 2 Pushback, 3 Bluer Pastures, 4 Seize the Means, 5 Of Production, 6 Pressing Forward, 7 Minesweeper, 8 Beenoculars, then currently scripted Uranus missions 9-11. Minesweeper and Beenoculars were added later but intentionally occur before the Uranus arc. Automated scenario-ready missions are IDs 0-6; Titania 7-8 are intentionally `InDevelopment`; 9-11 have trigger graphs but no current persisted campaign record.
- `SaveData/` contains local/testing user-data snapshots, not authoritative game design or campaign data. It can be deleted and must not be used to reconstruct intended missions. For current campaign intent, prefer `CampaignMissionCatalog`, `LevelIntro`, the runtime/server-backed level data, mission triggers, maps, obstacle prefabs, ship mechanics, and dialogue.
- `Scripts/Data/campaign_levels.json` is also older than the current mission sequence; it omits Pushback/Titania and maps IDs 2-8 to later missions. Before true end-to-end campaign qualification, verify the actual server-backed `campaign_levels_data` used at runtime and align it deliberately with `CampaignMissionCatalog`/`LevelIntro`.
- `CampaignScenarioIsolation` is the process-wide guard for isolated `Space` scene tests. It must be active before scene load so socket/audio bootstrap can suppress persistent/network side effects. Isolation has one owner at a time and should always be released by the scene host that acquired it.
- `CampaignScenarioSceneHost` loads the real `Space` scene additively, disables serialized `Behaviour`s on load, keeps the real Stage/prefab/pool references, creates an isolated Level/State shell, and owns teardown. It intentionally does not call the normal user-data/fleet bootstrap.
- Completed campaign setup methods are strongly coupled to real fleet spawning, command pools, menus, cutscene/dialogue state, camera/UI, and `ConfigData.CurrentShips`. `SavedSquad.GetAliveSquadShips()` resolves its `FleetShip`s through global `CurrentShips`, and `LevelConstructor` then requires full runtime ship stats/pool state. There is no existing isolated `CurrentShips`/fleet fixture. Do not run `CampaignMissionCatalog.Configure` in an automated scene test until that dependency is replaced or explicitly supplied; otherwise the test can read/mutate player data.
- Do not claim an end-to-end campaign test if it only scans source text or executes a parallel test-only mission graph. Full playthrough coverage should share the real objective logic while substituting user-data/UI/network side effects at explicit service boundaries.

## Campaign gameplay model

- The campaign is intended as one persistent attrition/resource war, not a sequence of independent RTS scenarios. Human ship losses persist, Bee losses persist, surviving Bee veterans can return, resource extraction changes future strength, retreat can preserve strategic value, and some mission results branch/skip later content. Preserve those cross-mission consequences when testing or refactoring level logic.
- Current mission IDs 0-11 are only the presently scripted arc. More campaign levels are planned. `Uranus3ANewThreat` currently behaves like an endpoint and unlocks broad post-campaign content, but that ending is temporary and must not be treated as the intended final narrative/gameplay conclusion.
- Pluto teaches the game then establishes persistence: 0 `Anomaly` is scripted exploration/discovery -> first Honeybee pursuit/combat -> reveal of a larger invasion; 1 `Reinforcements` is the fleet-control tutorial followed by a small elimination fight; 2 `Pushback` is the first straightforward fleet elimination battle; 3 `Bluer Pastures` is a timed Pluto defense/evacuation where casualties and evacuation performance determine future fleet strength and explicitly teach that both sides' losses matter strategically.
- Neptune is the resource-war arc: 4 `Seize the Means` is a dispersed assault on Bee forces around mining sites; winning unlocks Factories, while losing lets Bee-mined minerals become future Bee ships and skips the human mining mission. 5 `Of Production` is an escalating extraction/endurance mission: mine with Factories, defend them, and choose when to retreat as indefinitely growing Bee waves make greed increasingly dangerous. 6 `Pressing Forward` is a blockade-breaking elimination battle; failure costs the remaining human Factories, and the transition introduces Carrier-era gameplay.
- Titania is presently incomplete and must be interpreted with map/environment assets as well as trigger code. 7 `Minesweeper` is intended to be a navigation/avoidance encounter in which reaching Titania can be preferable to clearing the scattered Bee force; its commented MapObject/explosive discovery logic and `InDevelopment` status show that the minefield-specific mechanic is not fully represented by the current trigger graph alone. 8 `Beenoculars` is a prolonged multidirectional defense of an immobile Titania target; the authored `Resources/Obstacles/Bee-noculars.prefab` means its lanes/cover are part of the encounter, not decorative background.
- Uranus is currently the late-game escalation: 9 `On the Offensive` is an elimination offensive that introduces/teaches Carrier Strikers, Cruisers and Bumblebees; 10 `On the Defensive` is a harder late-game mining/extraction siege with retreat and large two-direction waves; 11 `A New Threat` is a Barge rescue/protection battle with reinforcement pressure and special Barge-state dialogue, currently followed by broad unlocks because it is the temporary campaign endpoint.
- Named campaign obstacles are runtime gameplay assets loaded from `Resources/Obstacles/{LevelOptions.Obstacles}`. `SpawnObstacles()` registers both `StaticObstacle` geometry and any embedded `MapObject`s, so a mission prefab can define pathing/cover plus interactive/destructible hazards. Qualification should load the exact authored prefab rather than replace it with generic obstacles.
- Obstacle geometry must be interpreted relative to ship clearance. Scouts/Hornets/Honeybees are tiny (~32-40 units), Frigates/Gunships/Wasps are small (~48), Cruisers/Dreadnoughts/Leafcutters medium (~64-84), Carriers/Bumblebees large (~96-136), and Factories/Barges are huge (~128-152). Narrow/angled corridors can therefore create materially different routes for scouts and capital/resource ships.
- Factory mining is spatial rather than abstract: mining-capable ships move to a `MiningAsteroid`, must physically touch its collider, then extract on a recurring timer; mining increases the miner's TSV and persistent `MineralsMinedThisLevel`. Thus Neptune mining missions are also escort/path-access problems, especially because the Factory is huge.
- Yellow Jackets are expendable contact bombers: a bombing run culminates in collision/detonation against the target, damaging the target and killing the Yellow Jacket. Their timed introduction in defense waves creates interception pressure rather than just another ranged DPS unit.
- Barges are huge charge/ram ships, not passive transports. They spend ~2 seconds winding up, charge at high speed, damage a contacted enemy while taking substantial reflected/self damage, then stop and cool down. `A New Threat` therefore mixes escort/rescue with protecting a valuable offensive unit whose charge state can expose it.
- Mission identity is defined by trigger code + current runtime level data + selected map + exact obstacle prefab + ship mechanics/clearance + spawn geometry + UI/dialogue. Do not infer campaign intent from `LeveLTriggers.cs`, `SaveData/`, or stale JSON in isolation.

## Fire Tank canister visuals

- Runtime object: `Scripts/Entities/CanisterBomb.cs`; serialized object: `Prefabs/Entities/Objects/Fire Tank.prefab`.
- `MapObject.Setup` calls the overridable `InitializeSprite`, and projectile damage calls `OnHealthChanged`. Specialized destructible visuals should use these hooks rather than duplicating `MapObject.OnTriggerEnter2D`.
- Fire Tank body sprites are grouped in `CanisterBomb.Sprites` as contiguous four-frame colour variants: grey stages 0-3, then red stages 0-3. Stage 0 is undamaged; stages advance at 25%, 50%, and 75% health lost.
- Unity sprite references in prefab YAML require both the texture GUID and each sub-sprite internal file ID. Read these from the texture `.meta` file's `nameFileIdTable`; do not use the texture's main file ID.
- `Sprites/Objects/smoke_puff.png` contains five 8x8 frames at 8 pixels per unit. The Fire Tank drives these directly from `CanisterBomb.Update` at 5 FPS; no Animator Controller or animation clip is required.
- Each damage stage after stage 0 enables one additional child `SpriteRenderer`. Smoke plume positions are serialized as `SmokePositions` on the Fire Tank prefab, so visual alignment can be tuned without code changes.
- The four Fire Tank frames are 530x165 at 40 pixels per unit. To convert a damage point from sheet-local pixels into prefab-local coordinates, use `x = (pixelX - 265) / 40` and `y = (82.5 - pixelY) / 40`. Current plume order follows the accumulating artwork: lower-right rupture, upper-shell damage, then the large left-side breach.
- Smoke children inherit the tank renderer's sorting layer and use sorting order +1. Their animation frame is offset per plume so multiple plumes do not pulse identically.

## Obstacle destruction debris

- Fire Tank obstacle destruction flows through `CanisterBomb.Kill()` -> `Obstacle.BreakApart(...)` -> normal `Obstacle.Kill()`. Keep the breakup geometry on `Obstacle`; callers provide the explosion origin, debris sprite set, and tuning values.
- `Obstacle.BreakApart` has its own `_breakApartStarted` guard, reset by `ClearData`. Do not repurpose `Obstacle.IsDead` as the breakup guard before calling virtual kill behavior, because subclasses may use `IsDead` as part of their own teardown contract.
- `Sprites/Obstacles/scrap_bits.png` contains 43 sliced fragment sprites. The current imported sub-sprites use lower-left pivots, so `ObstacleDebrisPiece` puts the `SpriteRenderer` on a centered child (`localPosition = -sprite.bounds.center`) and rotates the root. This avoids editing all sprite pivots and prevents visible orbiting during spin.
- Cosmetic obstacle fragments deliberately have no collider and no `Rigidbody2D`. `ObstacleDebrisPiece` moves/rotates its transform, exponentially damps velocity, fades after 60% of its lifetime, and destroys itself. This prevents debris from affecting combat, pathfinding, or physics.
- Debris spawn positions come from the destroyed obstacle collider bounds (renderer bounds are the fallback), so fragments appear to originate throughout the obstacle rather than from the explosion center. Launch direction is radial from the supplied explosion position with limited random spread.
- Debris randomness uses a local `System.Random` seeded from obstacle ID and explosion position. Do not use `UnityEngine.Random` for purely cosmetic debris because advancing the global Unity random state can interfere with deterministic simulation/replay work.
- Fire Tank debris tuning is serialized on `Prefabs/Entities/Objects/Fire Tank.prefab`: count, speed range, max spin, lifetime, damping, and scale range. Tune these visually before changing the algorithm.
- `AsteroidPiece` is the existing precedent for non-interacting destruction fragments, but Fire Tank obstacle debris is intentionally lighter because it does not need obstacle registration, Rigidbody2D physics, timers, or pooling.
- The current implementation instantiates/destroys cosmetic debris because Fire Tank detonations are infrequent. If profiling shows repeated explosions causing allocation/GC spikes, integrate `ObstacleDebrisPiece` with `Pool` rather than adding gameplay state to the fragments.

## Combat, targeting, and replay qualification

- `CombatLifecycleIntegrationTests` builds deterministic in-memory Stage/Level/GameState/Squad/Ship/FleetShip/SavedSquad/Weapon graphs without opening sockets or reading saves. Extend that pattern for simultaneous-death and many-ship scenarios rather than creating scene dependencies.
- `Ship.LogAttackingDamage` is guarded by `target.Health > 0` before logging/killing. Repeated lethal callbacks should therefore be idempotent for stats and release queues; mass-death tests should assert this invariant rather than adding a second death guard in the test harness.
- `RangeCollider` owns weapon-range enter/exit bookkeeping. Map-object visibility is shared derived state, so one range/contact exiting must not hide an object still observed elsewhere. The qualification branch uses `MapObjectVisibilityTracker` as the runtime companion owner rather than modifying `MapObject`, avoiding conflict with Fire Tank health/sprite hooks.
- Enter/exit tests should use multiple simultaneously tracked objects, multiple observing ranges, multiple colliders, deactivation, object destruction, and GameState reset so stale callback fields and missing ownership cannot hide behind a single-source happy path.
- Live replay input kinds are exactly `user-command`, `user-move`, `hivemind-matchup-response`, and `hivemind-command-response`. User commands encode `squadItemId|CommandType|enemySquadItemId`; user movement encodes comma-separated Squad `ItemId`s plus invariant-culture X/Y; Hive Mind responses should remain opaque server JSON.
- Replay checkpoints must sort squads/ships by stable IDs before serialization. Never use `HashSet`/dictionary iteration order as replay evidence. Useful deterministic checkpoint fields are terminal Level state plus ship health/TSV/death/lifecycle/position/velocity/rotation.

## Pathfinding and performance qualification

- Existing `BeesPerformanceQualification` is deliberately a CPU regression baseline: one path worker, a 64x64 open path grid, 25 real background searches, and 10,000 real `GameState.ResetState` calls. It is not minimum-spec certification.
- Static pathfinding obstacles are authoritative through `GameState.Obstacles`, and geometry is sampled from `Obstacle.ClearanceMappingCollider`. Dense tests must use real `Obstacle` + collider objects; mutating private clearance arrays bypasses the production ingestion path.
- Initial static obstacle ingestion is discovery-driven: `Pathfinder.InitializeMap()` calls `GameObject.FindGameObjectsWithTag("Obstacle")`, then `Obstacle.Setup(Level)`, which obtains IDs through `Stage.Pool`. Dense qualification fixtures therefore need the real `Obstacle` tag and at least a minimal real `Pool`; adding objects only to `GameState.Obstacles` is insufficient.
- Dynamic avoidance is rebuilt from live `CollisionAsteroid`/`AsteroidPiece` objects when `Level.ActivateCollisionAsteroids` is enabled. Production moving obstacles are registered after the base Pathfinder exists; stripped tests should mirror that lifecycle with `GameState.AddObstacle` + `Pathfinder.AddObstacle` instead of exposing a dynamic obstacle to initial static-map discovery. The dynamic layer is cached by `Stage.FixedUpdates`; a movement qualification test must advance that `int` value to force a new layer snapshot.
- Hardware qualification logs should record CPU/core count, RAM, GPU/VRAM/API, resolution, OS, Unity version, and whether Unity was running in batch/headless mode alongside PERF results. Thresholds become minimum-spec evidence only after running on named target machines.
- Long soak/performance tests should track both managed memory and stable pool/runtime baselines. Avoid unrealistically tight absolute memory values; qualification thresholds should catch monotonic growth/leaks and large regressions while remaining usable across supported machines.

## BeesServer and database contract

- Test/integration server mode must use MySQL database `bees_test`; normal/non-test server operation uses `ram`. The test database currently mirrors the live data so end-to-end tests can exercise realistic schema/data without touching live records.
- `ConfigData.Version` is part of the database contract. `ServerSettings.Fetch()` sends the exact version for `configuration`, `starting-settings`, and `ship-stats`; BeesServer performs an exact `(user/name/version)` query and does not safely fall back. Changing `ConfigData.Version` therefore requires matching settings rows whose serialized shape satisfies the current Unity parsers.
- The supplied full database dump contains global `configuration`, `starting-settings`, and `ship-stats` data for versions 2 through 7, including current Unity version 5. Version-5 data contains the current parser fields previously verified during qualification. Do not infer settings coverage from partial SQL search/extraction; inspect the full dump or query `bees_test` directly.
- Settings blobs are Unity-authored JSON-like text and can contain comments/trailing commas. Database qualification should verify row/version plus serialized required-field presence; actual parser compatibility belongs in Unity rather than Node strict `JSON.parse`.
- Hive Mind matchup IDs are deterministic unsigned xxHash64 values produced by BeesServer and kept as decimal strings in Node/MySQL `BIGINT UNSIGNED`. Unity `CommandResponse` and `MatchupStrategyResponse` now keep matchup IDs as strings as well; do not reintroduce signed `long` conversion for these identifiers.
- Hive Mind `strategy_id` values are persistent database schema even though their definitions live in BeesServer arrays. Current command IDs are 1-15 and targeting/shooting IDs 1-40. Reordering or reusing numeric IDs would reinterpret historical training data; append stable IDs or migrate data deliberately.
- The `OutcomeId` returned to Unity is a temporary server-Game-owned correlation ID, not the outcome table's auto-increment `ID`. Unity returns that ID with TSV in `store-commands`; only then does the server persist `(matchup_id, strategy_id, strategic_outcome)`. Reconnect must preserve the same server Game so unmatched outcome ownership survives transient disconnects.
- One completed Hive Mind command normally yields targeting, command, and shooting learning outcomes. The supplied dump contains exactly 1,210 accumulated `uses` in each of those three tables, a useful cross-layer sanity check.
- `stored_user_data` is opaque JSON keyed logically by `(userId, filename)`. `ID` is its primary key. Missing ordinary user rows are expected: `Socket.HandleUserDataResponse` generates/writes the appropriate default data and retries. Current server code forces `campaign_levels_data` and `challenge_levels_data` to synthetic shared user ID `2`; never use ID 2 for test users.
- BeesServer schema migration code adds hot lookup indexes for `stored_user_data(userId, filename, ID)` and `settings(userId, name, version, Id)`. Test-live migration targets only `bees_test`; production migration requires an explicit opt-in.
- For server-side schema/learning details use `BeesServer/docs/DATABASE_MODEL.md`; server live qualification validates the schema/settings contracts against `bees_test`.
