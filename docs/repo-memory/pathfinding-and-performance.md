# Pathfinding and performance

- Existing `BeesPerformanceQualification` is a CPU regression baseline, not minimum-spec certification: one path worker, a 64x64 open grid, repeated real background searches, and repeated `GameState.ResetState` calls.
- Pathfinder Unity obstacle discovery must be scoped to the owning `Level.Map` hierarchy. Never use scene-global obstacle discovery on a Stage that can host multiple simultaneous Levels; doing so can reassign another Level's obstacles and corrupt their pathfinding ownership/indexes.
- Pathfinder grid coordinates are Level-local, but Unity `Physics2D` and collider APIs use world space. Convert collider bounds/closest points world→Level before grid mapping, and convert Level-local entity/grid points Level→world before `Linecast`, `OverlapPoint`, `BoxCast`, or other physics queries. Turret/Charge obstacle tests must add the owning `Level` position just like collider-based targeting already does.
- Training/reset must retire the current Pathfinder instance rather than reinitialize its worker arrays while background `Task.Run` searches may still be active. Old workers may finish on the retired instance; lifecycle/request IDs still guard whether their result is applied.
- `Pathfinder.InvalidatePathRequest()` invalidates only the result identity; it does not cancel the active `Task.Run` search, which can continue until the path search time limit. Periodic movement refreshes must therefore not call `MoveToPoint()` while `Ship.IsPathfinding` is true. Let the live search settle, then refresh the destination on a later timer tick. This applies to moving attack/friendly/guard targets, circle movement, bomber return-to-carrier, healing targets, recurring retreat destinations, and collision-asteroid rechecks.
- `Aggressive` pursuit has a stronger ownership requirement than a simple `!IsPathfinding` guard. It must use `Ship.MoveToTrackedPoint()`, which preserves an active A* worker, honors `_tryingToFindPathAgain` failure backoff, keeps a useful `IsFollowingPath` route until the enemy endpoint has moved at least two path cells, and rate-limits moving-target replans to one per second. A recurring 0.25-second attack timer must never become the owner of a fresh A* request merely because the previous worker finished.
- `Ship.MoveToPoint()` must ignore an identical in-flight timer/order destination instead of invalidating a still-useful worker, but a newly detected collision obstacle (`foundObstacle=true`) is a topology change and must still be allowed to invalidate the previous snapshot once.
- Never emit frame-rate diagnostics for long-running path workers from `Pathfinder.Update()`. A worker is allowed to search for several seconds; logging every rendered frame while a queue is waiting adds main-thread work precisely when pathfinding is already saturated.
- Combat freeze diagnostics are opt-in through `Level.EnableFreezeDiagnostics`, separate from the heavy `DebugLogger.IsDebugging` mode. They aggregate once per real-time second and report worst frame time, Aggressive ticks, tracked-pursuit A* requests, queue/worker pressure, HiveMind sight events, weapon-range entries, turret candidate work, projectiles, and timer count. Do not replace aggregate diagnostics with per-contact/per-worker logging.
- HiveMind side-wide visibility is maintained incrementally in `GameState.VisionCache`. `HivemindShips` remains the per-observer attribution graph, while `RecordHiveMindSighting()` updates both structures. `GetShipsVisibleToHiveMind()` must return the maintained cache rather than aggregating every observer set on each pairwise trigger event; first contact between dense squads otherwise multiplies main-thread set traversal and allocation.
- Weapon `ShipsWithinRange` is an enemy-candidate cache, not a raw physics-contact cache. `RangeCollider` must reject same-side ships before inserting them or creating reverse `WeaponsThatHaveUsWithinRange` ownership, and target validation should retain an enemy-side guard as defense in depth.
- Physics-tick targeting scans must stay linear in ships within range. In particular, never index `Dictionary.Values` through LINQ `ElementAt(i)` in a loop: `Dictionary.ValueCollection` is not indexable, so repeated `ElementAt` calls re-enumerate from the beginning and turn the scan quadratic. Iterate `ShipsWithinRange.Values` directly.
- Squad bounds/centers are combat hot-path geometry. Calculate all four bounds in one linear pass; do not independently `OrderBy` the ship list for left/right/top/bottom points. Distance-based targeting may invoke squad position repeatedly from inside a sort comparator, so hidden sorting inside `GetPosition()` is multiplicative.
- `Pathfinder` is intentionally decomposed into core coordinate/result ownership, `Pathfinder.Obstacles.cs`, `Pathfinder.Search.cs`, `Pathfinder.Models.cs`, and `PathfinderObstacleScope.cs`. Keep new behavior in the appropriate focused file rather than recreating the monolith.
- Static pathfinding obstacles are authoritative through Level-scoped obstacle geometry sampled from `Obstacle.ClearanceMappingCollider`. Dense qualification should create real Obstacles/colliders rather than mutating private path arrays.
- Dynamic collision-asteroid avoidance is a separate cached layer rebuilt from live moving obstacles when enabled. Tests should register dynamic obstacles after base Pathfinder initialization and advance `Stage.FixedUpdates` to force a new layer snapshot.
- Authored obstacle layouts can be gameplay rules, not decoration. Placement/spawn/path qualification should inspect the exact mission prefab and use real collider geometry plus ship clearance.
- Hardware qualification should record CPU/core count, RAM, GPU/VRAM/API, resolution, OS, Unity version, and batch/headless status alongside performance results.
- Soak tests should watch both managed memory and stable pool/runtime counts. Prefer monotonic-growth/leak assertions over unrealistically tight absolute memory thresholds.
