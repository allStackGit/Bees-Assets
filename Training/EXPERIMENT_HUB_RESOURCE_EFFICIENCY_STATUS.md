# Resource-efficient training workstream

Updated 2026-11-12. Branch: `feat/hub-resource-efficiency-20261112`.
Scope: TinyBrains, Courier, future native projects; Bees remains with the unified native rewrite.
The Hub reserves **fixed** CPU/RAM/GPU and machine allocations. Backends optimize useful training throughput inside those leases.

## Implemented code, not yet live-system qualified

- **Existing Hub metrics pipeline:** derives sustained collection-vs-optimization and rollout engine-vs-inference work shares from measured durations, with five-of-six sustained signals for dominant remote-collector join waits or learner rollout-merge overhead when independently timed. Remote requests now report worker receive/decode, learner serialize/compress/send/receive/decode/ingestion and compressed wire bytes separately; socket blocking and roundtrip residual are **not** claimed as physical network saturation or bandwidth. Checkpoint save stalls are timed. These measurements enter the existing Train/Monitor/Compare archives, selection and exports. The validated source now allows up to 512 named measurements, still with the strict 32-KiB serialized report cap; the separate chart cache remains limited to 96 selected measurements.
- **Companion backend branch:** `allStackGit/TinyBrains:feat/hub-resource-efficiency-20261112` based on `feat/linux-tinybrains-runtime`. Persistent local and remote collectors can use a pool of independent one-match native engines. Native steps run concurrently while policy observations stay batched. A RAM-bounded controller calibrates concurrency on sustained usable actions/s, accepts a clear gain or retires engines at completed episodes and settles without restarting the whole pool. Each engine has one Rayon thread; the dispatch pool no longer imposes an artificial 64-concurrent-engine ceiling on hosts with larger CPU leases.
- **GPU execution:** persistent colony PPO partitions *unchanged minibatches* into VRAM-budgeted microbatches rather than an unconditional 65,536-pixel ceiling. Colony PPO rollout inference coalesces policy results across distinct board shapes into one host readback where safe, preserving seeded sampling order and per-seat record ordering. Optional CUDA/ROCm profiling now brackets optimization work with stream events and reads their interval only after an existing synchronization; this measures an elapsed device-stream interval, **not** exclusive GPU utilization. Existing two-GPU optimization/collection device separation remains intact.
- **Heterogeneous collectors:** immutable per-update shares of the fixed total PPO action target can shift toward higher delivered actions/s. Adjustments require sustained samples and a predicted ≥18% gain, then an observed ≥10% benefit to accept; otherwise revert and settle. Fixed operator weights retain precedence. Restored allocations are accepted only from a checkpoint-aligned source history and original collector identities.
- **Hub launch/measurement integration:** both native platform ownership contexts provide frozen RAM budgets. Trusted TinyBrains persistent and remote launchers opt into these capabilities when the installed backend supports them; older backends retain legacy execution. Per-machine simulation pool size, memory, accepted/rejected tuning and GPU batch measurements all use existing trusted `hub-metrics-v1` fields.

## Significant remaining development

1. **Exercise the exact executable native-engine path:** qualify pooled episode/seat identity, replay attribution, graceful retirement and checkpoint continuation using actual TinyBrains binaries and training environments. Only the source contracts and targeted synthetic/checking paths have been inspected here; throughput gains are not yet measured.
2. **Courier trainer integration:** the Hub Courier adapter still controls a fixed `--workers` count. The trusted external `courier.py` training implementation is not in the accessible Bees-Assets/TinyBrains repositories or available as a relevant Library source. Its environment lifecycle and CPU/GPU execution semantics must be inspected before introducing equivalent safe autosizing and batching; no completed Courier autoscaling is claimed.
3. **GPU utilization and multi-GPU:** quantify real microbatch/large-batch throughput and VRAM headroom. Improve GPU inference/optimizer execution for each allocated device as evidence requires, including efficient support where two or more devices actually contribute useful work without changing learning semantics.
4. **Bottleneck attribution:** the remote framing, codec, ingestion, merge and wait boundaries are now timed, but the source still needs independent server response serialization, actual queue occupancy/pressure, GPU kernel vs host synchronization, and physical CPU/RAM/VRAM/network capacity attribution. The stage signals remain diagnostic evidence, not certified hardware saturation.
5. **Safe continuation and cross-project adoption:** verify stable pool sizing and balancing across checkpoint resumptions and interruptions; expose reusable backend contracts for future projects without adding a new Hub scheduler.

Keep the separate Hub feature-development and Bees rewrite workstreams unaffected. Do not interpret code presence, CPU/GPU busy percentage, or old training logs as proof of scaling.
