# Resource-efficient training workstream

Updated 2026-11-12. Branch: `feat/hub-resource-efficiency-20261112`.
Scope: TinyBrains, Courier, future native projects; Bees remains with the unified native rewrite.
The Hub reserves **fixed** CPU/RAM/GPU and machine allocations. Backends optimize useful training throughput inside those leases.

## Implemented code, not yet live-system qualified

- **Existing Hub metrics pipeline:** derives sustained collection-vs-optimization and rollout engine-vs-inference work shares from measured stage durations, plus remote collector turnaround residual when independently reported service time exists. Distinguishes timing dominance from hardware saturation; stages with incomplete evidence are not guessed. Retains the standard Train/Monitor/Compare history and full observation exports. The bounded wire source limit now accepts up to 384 metrics (still 32 KiB per report), enough for nine fully profiled TinyBrains collectors; chart downselection remains separate.
- **Companion backend branch:** `allStackGit/TinyBrains:feat/hub-resource-efficiency-20261112` based on `feat/linux-tinybrains-runtime`. TinyBrains persistent local and remote collectors can now use a pool of independent one-match native engines. CPU work runs in parallel across engine subprocesses while actor/critic observations remain batched together. A RAM-bounded controller probes more concurrency using sustained usable actions/s, then accepts a clear gain or retires engines after completed episodes and settles. Environments already running are never restarted as a group. Each engine has one Rayon thread to avoid N×N native thread oversubscription.
- **GPU execution:** persistent colony PPO partitions *unchanged minibatches* into VRAM-budgeted microbatches rather than an unconditional 65,536-pixel ceiling. Colony PPO rollout inference coalesces policy results across distinct board shapes into one host readback where safe, preserving seeded sampling order and per-seat record ordering. Existing two-GPU optimization/collection device separation remains intact.
- **Heterogeneous collectors:** immutable per-update shares of the fixed total PPO action target can shift toward higher delivered actions/s. Adjustments require sustained samples and a predicted ≥18% gain, then an observed ≥10% benefit to accept; otherwise revert and settle. Fixed operator weights retain precedence. Restored allocations are accepted only from a checkpoint-aligned source history and original collector identities.
- **Hub launch/measurement integration:** both native platform ownership contexts provide frozen RAM budgets. Trusted TinyBrains persistent and remote launchers opt into these capabilities when the installed backend supports them; older backends retain legacy execution. Per-machine simulation pool size, memory, accepted/rejected tuning and GPU batch measurements all use existing trusted `hub-metrics-v1` fields.

## Significant remaining development

1. **Exercise the exact executable native-engine path:** qualify pooled episode/seat identity, replay attribution, graceful retirement and checkpoint continuation using actual TinyBrains binaries and training environments. Only the source contracts and targeted synthetic/checking paths have been inspected here; throughput gains are not yet measured.
2. **Courier trainer integration:** the Hub Courier adapter currently controls a fixed `--workers` count. The trusted external `courier.py` training implementation is not part of the mounted Bees-Assets/TinyBrains sources. Its environment lifecycle and CPU/GPU execution semantics must be inspected before introducing equivalent safe autosizing and batching; no completed Courier autoscaling is claimed.
3. **GPU utilization and multi-GPU:** quantify real microbatch/large-batch throughput and VRAM headroom. Improve GPU inference/optimizer execution for each allocated device as evidence requires, including efficient support where two or more devices actually contribute useful work without changing learning semantics.
4. **Bottleneck attribution:** instrument independently measured ingestion/serialization/queue and network path stages to separate software throughput limits from physical CPU/GPU/RAM/VRAM/network saturation, maintaining honest uncertainty and per-machine identity. Current stage shares are not definitive resource-capacity diagnoses.
5. **Safe continuation and cross-project adoption:** verify stable pool sizing and balancing across checkpoint resumptions and interruptions; expose reusable backend contracts for future projects without adding a new Hub scheduler.

Keep the separate Hub feature-development and Bees rewrite workstreams unaffected. Do not interpret code presence, CPU/GPU busy percentage, or old training logs as proof of scaling.
