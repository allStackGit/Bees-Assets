# Resource-efficient training workstream

Updated 2026-11-12. Branch: `feat/hub-resource-efficiency-20261112`.
Scope: TinyBrains, Courier, future native projects; Bees remains with the unified native rewrite.
The Hub reserves **fixed** CPU/RAM/GPU and machine allocations. Backends optimize useful training throughput inside those leases. Benchmarks below are not implied: these are source-level changes awaiting real workload qualification.

## Implemented code, not yet live-system qualified

- **Existing Hub metrics pipeline:** derives sustained collection-vs-optimization and rollout engine-vs-inference work shares from measured durations, with five-of-six sustained signals for dominant remote-collector join waits or learner rollout-merge overhead when independently timed. Remote requests now report worker receive/decode, learner serialize/compress/send/receive/decode/ingestion and compressed wire bytes separately; socket blocking and roundtrip residual are **not** claimed as physical network saturation or bandwidth. Each collector reports CPU observation preparation and opponent-processing time separately from inference and native stepping. Parallel pools report **simulation_match_steps**: actual independent native match transitions, not just the legacy aggregate `engine_steps` tick count. Default throughput charts prioritize usable decisions/s and real simulation match steps/s. Checkpoint save stalls are timed. These measurements enter existing Train/Monitor/Compare archives, selection and exports. The validated source allows up to 512 named measurements with a strict 32-KiB report cap, and the chart cache holds up to 96 operator-selected measurements. Near the 32-KiB cap, the analyzer preserves the highest-priority derived evidence that fits instead of dropping all derived findings. Sustained (five-of-six, at least two minutes) **per-collector** engine/observation/inference/opponent stage dominance is exposed through the same metrics, default charts, and Train/Monitor summaries; it is explicitly not a device-saturation claim. Native engine pools now also report per-collector dispatch-thread queue wait, summed child roundtrip wall, whole-batch wall, last-child completion gap and an effective in-flight request factor. The Hub distinguishes sustained slow-child barriers, dispatch queueing, and remote rollout record packing (now independently timed at the worker) from GPU and hardware saturation claims. The 32-KiB/512-metric source contracts still apply.
- **Companion backend branch:** `allStackGit/TinyBrains:feat/hub-resource-efficiency-20261112` based on `feat/linux-tinybrains-runtime`. Persistent local and remote collectors can use a pool of independent one-match native engines. Native steps run concurrently while policy observations stay batched. A RAM-bounded controller calibrates concurrency using sustained usable actions/s in either direction: it probes upward first, then tests lower concurrency if the original CPU-sized pool appears oversubscribed. Probes use long windows, cooldowns, measured improvement thresholds, rollback, and a settled state. Throughput uses **all actions and collection seconds in each full window**, not the latest eight updates; the recent samples only check variability. Reductions retire environments after completed episodes without restarting the pool. Large hosts can probe a meaningful halving to escape severe throughput-collapse plateaus. Each engine has one Rayon thread; the dispatch pool no longer imposes an artificial 64-thread dispatch ceiling; the previous fixed 128-engine ceiling is now 512 subject to the same leased CPU/RAM and measured admission limits. New local and remote pools start near their leased CPU count instead of a fixed eight-engine bootstrap, subject to the same per-engine RAM-admission guard and later sustained throughput tuning. Removed a separate fixed 128-MiB-per-engine cap; live child-process RSS and parent RSS under the frozen lease are the admission authority. CPU-only collectors now dispatch independent ONNX opponent inference through a small bounded pool rather than serializing all opponent sessions. Fog-memory learner **and Torch-opponent** paths now build each policy observation and next memory state from the same encoded board instead of reconstructing every board twice. A checkpoint-aligned proven concurrency count can be reused when restarting an equivalent run on the same host/lease/workload; fresh jobs with separate histories still calibrate independently.
- **GPU execution:** persistent colony PPO partitions *unchanged minibatches* into VRAM-budgeted microbatches rather than an unconditional 65,536-pixel ceiling. Colony PPO rollout inference coalesces policy results across distinct board shapes into one host readback where safe, preserving seeded sampling order and per-seat record ordering. Frozen/current Torch-opponent inference now coalesces deterministic actions across shapes per model as well. Singleton shape groups in the learner, opponent, PPO cache and uncached PPO paths avoid unnecessary NumPy host copies while preserving board shapes. Repeated PPO rollout boards are staged once on the optimizer GPU across multiple epochs only when a conservative 4%-of-free-VRAM / 256-MiB budget permits it; otherwise the prior per-microbatch transfer path remains. The cached values retain their source dtype, and PPO minibatch composition and optimizer steps do not change. Optional CUDA/ROCm profiling now brackets optimization work with stream events and reads their interval only after an existing synchronization; this measures an elapsed device-stream interval, **not** exclusive GPU utilization. Existing two-GPU optimization/collection device separation remains intact.
- **Heterogeneous collectors:** immutable per-update shares of the fixed total PPO action target can shift toward higher delivered actions/s. Adjustments require ≥90-second full-window delivered-actions/elapsed-time evidence, a predicted ≥18% gain, and an observed ≥10% benefit to accept; otherwise revert and settle. The 30-update cooldown excludes transient updates from the following calibration window rather than allowing them to distort the rate. Fixed operator weights retain precedence. Restored allocations are accepted only from a checkpoint-aligned source history and original collector identities.
- **Hub launch/measurement integration:** both native platform ownership contexts provide frozen RAM budgets. Trusted TinyBrains persistent and remote launchers opt into these capabilities when the installed backend supports them; older backends retain legacy execution. The persistent TinyBrains adapter now defaults its CPU thread count to the **Hub-leased CPU allocation** rather than a separate profile default, while explicit per-job thread overrides and the legacy profile setting remain supported. Per-machine simulation pool size, proven/restored settings, memory, accepted/rejected tuning, optimizer board-cache bytes/reuses and opponent inference batching all use existing trusted `hub-metrics-v1` fields.

## Significant remaining development

1. **Exercise the exact executable native-engine path:** qualify pooled episode/seat identity, replay attribution, graceful retirement and checkpoint continuation using actual TinyBrains binaries and training environments. Only the source contracts and targeted synthetic/checking paths have been inspected here; throughput gains are not yet measured.
2. **Courier trainer integration:** the Hub Courier adapter still controls a fixed `--workers` count. The trusted external `courier.py` training implementation is not in the accessible Bees-Assets/TinyBrains repositories or available as a relevant Library source. Its environment lifecycle and CPU/GPU execution semantics must be inspected before introducing equivalent safe autosizing and batching; no completed Courier autoscaling is claimed.
3. **GPU utilization and multi-GPU:** quantify real microbatch/large-batch throughput and VRAM headroom. Improve GPU inference/optimizer execution for each allocated device as evidence requires, including efficient support where two or more devices actually contribute useful work without changing learning semantics.
4. **Bottleneck attribution:** independently timed remote framing, codec, record packing, ingestion, merge, wait and per-collector stages now support conservative stage-dominance signals. Child-dispatch queue waiting and slowest-child completion tails are measured, but this is not equivalent to native-engine CPU busy time. Remaining gaps include worker response-frame serialization, actual queue occupancy and distributed backpressure, GPU kernel versus host synchronization, and reliable physical CPU/RAM/VRAM/network capacity attribution. Current signals do not prove hardware saturation.
5. **Safe continuation and cross-project adoption:** qualify checkpoint-aligned simulation sizing across actual restarts and extend proven-profile reuse beyond one run directory without weakening resource/workload identity or adding a new Hub scheduler. Courier and future project backends still require their own executable pool/batching integrations.

Keep the separate Hub feature-development and Bees rewrite workstreams unaffected. Do not interpret code presence, CPU/GPU busy percentage, or old training logs as proof of scaling.
