## Implemented in this branch (software capability, not production qualification)

- **Coordinator and native ownership:** standalone Linux/Windows-capable control plane, authenticated machine enrollment/heartbeat, fresh agent-instance and capacity receipts, machine-local systemd/Windows Job Object supervision, durable native dispatch journals, Stop/Inspect reconciliation, process/resource usage reporting, native GPU identity/probes and explicit GPU claims.
- **Configuration and scheduling:** revisioned saved project configurations, immutable queued jobs, resource/admission previews, multi-project CPU/GPU allocation, frozen independent sequences/trials, multi-stage checkpoint continuations, atomic 2–16-job mixed-project resource bundles. Bundle members receive **one atomic native Start authorization** and **one confirmed group shutdown**, plus an explicitly approved future group launch that waits for fresh machine/lease/native readiness. CPU-only launch approval can survive coordinator restart with separate consent; GPU approval cannot. All group operations preserve independent native ownership and release claims only after safe receipts. No simultaneous process-start guarantee or common learning protocol.
- **Unattended CPU operation:** explicitly armed native queue scheduler, project-fair scheduling, native admission and terminal lease cleanup, CPU-only opt-in restart/agent recovery after fresh native reconciliation. Uncertain or failed native owners require operator review; GPU scheduling is separately authorized.
- **Stopping, selection, and continuation:** single- or same-checkpoint multi-suite independent evaluation gates, checkpoint-preserving Stop and verified continuation eligibility, final checkpoint fingerprint/evaluation ownership, reinspection, scheduled competing-candidate ranking and model-pinned promotion for supported projects.
- **TinyBrains distributed path:** atomically reserved learner/remote-collector group, pinned tailnet/HMAC endpoints, verified on-policy collector barrier, **one bounded unattended approval from group reservation through native collector Starts to GPU learner Start**. An operator may approve before all lease receipts/GPU probes complete. The control plane freezes original machine/lease/ordered endpoint identity, commits all native collector Starts with the future learner authorization, optionally preserves explicit pending recovery across coordinator restart, and still requires fresh verified original native collector owners/HMAC/GPU proof. Native sidecar teardown/aborted-startup cleanup, verified terminal release, frozen per-collector action weights and source-independent rollout metrics are implemented. Deliberately separate from ordinary resource bundles.
- **Supported adapters and evaluators:** original Courier and TinyBrains native adapters provide frozen configuration/profile validation, checkpoint-ready/lineage and model identity checks, platform-specific native Stop, progress, independent suite receipts, scheduled evaluation and same-checkpoint threshold enforcement. Source review found no missing parallel adapter or evaluator *interface* to implement. Windows/Linux runtime qualification is distinct from this code coverage.
- **Operator surfaces:** Design, Train, Monitor, Compare, Machines, independent evaluation/ranking, candidate selection, grouped queue lifecycle controls, native diagnostics and exports; common authenticated agent protocol and shared loopback operator API on standalone and integrated coordinator entry points. ## Resource-efficiency workstream (separate from native scheduling completion)

- **Implemented in source, not benchmark-qualified:** TinyBrains persistent PPO now reports per-collector inference batch sizes, engine subprocess CPU/RSS, rollout encoding/inference/engine/processing host-wall intervals, remote request/response/encoding time, learner collection wait, collector critical-path/spread, and checkpoint stalls. It now rebalances the *fixed total* PPO action target across heterogeneous assigned collectors from eight sustained useful action-rate samples (12% predicted critical-path gain, bounded ~20% changes, 32-update cooldown), caches advisory weights keyed to its runtime identity, and always honors explicit fixed weights. A collector's target freezes before its on-policy work is submitted. The optimizer combines finite-loss and detached metric readbacks into one GPU transfer per PPO minibatch without changing effective minibatches or the policy-version boundary.
- **Common metric path:** `experiment_hub_tinybrains_persistent_adapter.js` publishes these observations through the same project-neutral progress contract, chart selection, append-only observations, comparison, and export paths used for other projects. The validated source metric envelope is bounded at 640 fields / 48 KiB, with up to 64-character names; the 96-field chart projection and 64-KiB agent heartbeat/archive limits remain separate. The 17-collector mapped sample is source-validated; no live run has measured a speedup.
- **TinyBrains local CPU execution (implemented in source, not yet benchmark-qualified):** Hub-owned persistent PPO runs without remote collectors now use a retained original multi-match official engine as the batched-inference baseline, with independent one-match subprocess slots added one at a time only after sustained useful SPS calibration. Each new process receives one Rayon thread; the existing base engine keeps its original settings. Candidate counts require eight stable samples, a 10% useful throughput gain, and long cooldowns; ineffective candidates drain only after their own live episode ends. Matching runtime identity profiles preserve accepted counts. The Hub freezes CPU/RAM leases; the backend checks per-process RSS and conservative remaining RAM before adding slots. CUDA snapshot events protect on-policy reads across worker streams. Original PPO action targets and policy-version validation remain unchanged.
- **Hub metrics:** Existing project-neutral progress/observation/chart/export paths now receive local-engine active/max/retiring counts, useful action rate, individual slot timings and RAM, process CPU totals, critical-path wall time, and explicitly labeled *summed overlapping* stage durations. These measurements are not proof of hardware saturation or performance improvement.
- **Current TinyBrains backend integration (development branches):** The existing persistent adapter now preserves additional per-worker native simulation, observation/inference, CPU pool sizing and remote transport/ingestion timing fields; it also publishes explicitly uncertain stage-delay candidates as numeric chartable metrics through the same Hub progress/observation/export path. The companion TinyBrains backend branch `feat/remote-reuse-stable-pool-profile-20261113` adds settled remote pool calibration persistence, Linux ROCm single-device inference collectors and source diagnosis. This integration is unmerged and has not had live multi-machine validation.
- **GPU PPO execution (additional development branches):** TinyBrains `feat/ppo-adaptive-microbatch-20261113` probes bounded hardware microbatch pixel budgets after sustained comparable completed-update measurements, with a 10% minimum observed improvement, rejection rollback, cooldowns, and checkpoint-aligned performance-hint recovery. Its PPO minibatches, records, epochs, optimizer-step count and policy-version boundaries remain fixed. Hub `feat/hub-ppo-autobatch-metrics-20261113` exposes processed PPO board-state/pixel rates (not unique training SPS), budget/factor, calibration progress and accepted/rejected changes through existing project-neutral charts, histories and exports. These are unmerged development changes; no useful-SPS gain is established.
- **Still substantial:** Episode-safe TinyBrains EnginePool expansion is implemented in local and remote PPO collectors, but heterogeneous throughput calibration and integrated deployments remain unqualified. Courier does not yet have episode-safe dynamic parallelism. GPU inference batching is not tuned; general GPU execution/device assignment, simultaneous multi-GPU PPO optimization, and corroborated cross-machine primary/overlapping bottleneck classification remain. CPU/RAM/GPU optimization and benefit require real throughput qualification.
- **Next priorities:** tune cross-engine GPU inference efficiently while preserving action RNG/episode semantics, then adapt Courier through a small trusted backend interface. Extend diagnosis with observed machine/worker utilization and queue evidence while retaining unknown/overlap when insufficient. Defer larger integrated benchmarks until implementation is substantially complete.
