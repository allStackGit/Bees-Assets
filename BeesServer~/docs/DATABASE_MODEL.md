# Bees database model

This document describes how the current MySQL/MariaDB data model is used by BeesServer and the Unity client. It combines the complete August 8, 2026 `ram.sql` reference dump with the migrations and live-schema requirements in the current repository.

`bees_test` mirrors the supplied live data for qualification and is migrated by the canonical test path before live tests run. Automated integration work must use `bees_test`; normal non-test server startup uses `ram`.

## Source-of-truth distinction

Do not confuse the **reference dump schema** with the **current migrated runtime/test schema**:

- the August 8 dump records the schema as it existed when exported;
- `schemaMigrations.js` widens selected columns and adds hot lookup indexes idempotently;
- `test/databaseSchema.live.test.js` defines the current schema properties that qualification requires after migration.

When current code/schema behavior matters, migrated metadata and live-schema tests outrank the pre-migration dump definition. Dump row counts and AUTO_INCREMENT values remain useful historical/capacity evidence.

## High-level model

The database has five application tables:

- `settings` — versioned server-provided game configuration/settings payloads;
- `stored_user_data` — player/template save-data and durable metadata keyed logically by user and filename;
- `strategic_commands` — learned command/movement strategy outcomes;
- `shooting_outcomes` — learned shooting strategy outcomes;
- `targeting_outcomes` — learned enemy-squad targeting outcomes.

There are no relational matchup or strategy lookup tables. Matchups are deterministic xxHash64 identifiers generated by BeesServer, while strategy IDs are implicit persistent references to hard-coded registries in `Game`.

## Current migrated schema requirements

### `settings`

Current qualification requires:

```text
Id           INT          PRIMARY KEY AUTO_INCREMENT
userId       BIGINT       NOT NULL DEFAULT 0
version      INT          NOT NULL
name         VARCHAR(45)
contents     LONGTEXT
created_date DATETIME     DEFAULT CURRENT_TIMESTAMP
edited_date  DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

Logical lookup identity is `(userId, name, version)`, with the newest `Id` winning when multiple rows are returned. Current migration ensures a composite index beginning with `(userId, name, version, Id)`.

The August 8 dump had `settings.userId INT` and only the primary-key index; those statements describe the raw reference dump, not the post-migration qualification schema.

### `stored_user_data`

Current schema:

```text
ID           INT          PRIMARY KEY AUTO_INCREMENT
userId       BIGINT       NOT NULL
filename     VARCHAR(255) NOT NULL
contents     LONGTEXT     NOT NULL
created_date DATETIME     DEFAULT CURRENT_TIMESTAMP
edited_date  DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

Logical lookup identity is `(userId, filename)`, normally choosing the newest `ID`. Current migration ensures a composite index beginning with `(userId, filename, ID)`.

The supplied dump contains 282 rows across 32 user IDs and had next AUTO_INCREMENT 19,485. The dump lacked that secondary logical-lookup index; migration now supplies it.

`stored_user_data` also carries internal durable metadata using reserved filenames, including Hive Mind OutcomeId reservations such as `__hivemind_outcome__:<id>`. Those records are server-owned protocol state, not ordinary player files.

### Outcome tables

`strategic_commands`, `shooting_outcomes`, and `targeting_outcomes` currently require:

```text
ID                INT UNSIGNED        PRIMARY KEY AUTO_INCREMENT
matchup_id        BIGINT UNSIGNED     NOT NULL
strategy_id       TINYINT UNSIGNED    NOT NULL
strategic_outcome MEDIUMINT           NOT NULL
uses              BIGINT UNSIGNED     NOT NULL DEFAULT 1
```

Each has an index beginning with `matchup_id`. The August 8 dump had `uses MEDIUMINT UNSIGNED`; `schemaMigrations.js` deliberately widens all three `uses` columns to `BIGINT UNSIGNED`, and the live schema test requires the widened type.

Reference-dump summary:

| table | rows | distinct matchups | strategy ID range observed | total uses | next AUTO_INCREMENT |
|---|---:|---:|---:|---:|---:|
| `strategic_commands` | 1,014 | 706 | 1–15 | 1,210 | 871,719,858 |
| `shooting_outcomes` | 1,110 | 699 | 1–36 | 1,210 | 945,973,486 |
| `targeting_outcomes` | 806 | 84 | 1–40 | 1,210 | 578,549,269 |

The matching total `uses` in that snapshot is consistent with the three Hive Mind learning layers being updated together; it is historical evidence, not a schema invariant.

## Account/user identity

Steam64-sized user IDs can exceed JavaScript's exact integer range. Preserve them as exact decimal strings across Node logic when necessary.

`database.js` enables MySQL big-number string handling and normalizes returned `userId` values to decimal strings. Authentication compares the claimed request user to the exact authenticated Steam identity rather than converting either through JavaScript `Number`.

This is separate from:

- WebSocket/request hash identity;
- server `Game` identity;
- temporary Hive Mind `OutcomeId` identity;
- deterministic matchup hash identity;
- physical database row `ID`.

Do not substitute one namespace for another.

## Settings contract

Unity requests settings using `ConfigData.Version`; BeesServer performs exact user/name/version lookup and does not invent an automatic version fallback. User-specific settings can override global user 0.

Current Unity uses version 5. The reference dump contains all three matching global version-5 rows:

- `configuration` v5 (`Id` 14);
- `starting-settings` v5 (`Id` 15`);
- `ship-stats` v5 (`Id` 16`).

The payloads contain the current fields expected by Unity, including configuration carrier/squad-save fields, starting-fleet arrays, and ship-stat TSV/projectile/sound fields.

The blobs may contain syntax accepted by Unity's Newtonsoft readers that strict `JSON.parse` would reject, such as comments/trailing commas. Unity's actual deserializer is the compatibility authority for those payloads.

Versions 6 and 7 also exist in the dump, but their presence does not change the exact-current-version contract.

## Matchup and strategy identity

`Common.stringToInt64(input)` computes xxHash64 and represents the unsigned 64-bit result as a decimal string for MySQL `BIGINT UNSIGNED`. Never coerce matchup hashes to JavaScript `Number`.

`strategy_id` is persistent data schema even though its meaning is defined in code. Current registries are:

- command strategies: IDs 1–15;
- targeting strategies: IDs 1–40;
- shooting strategies: IDs 1–40.

The reference dump observed shooting IDs 1–36, but code supports 1–40. Do not reorder or repurpose existing numeric strategy IDs without migrating historical data and coordinating Unity name/type mappings.

### Learning-key namespaces

Current targeting and shooting matchup strings are deliberately namespaced with corrected formats:

- `target-v2:` for targeting history;
- `shoot-v2:` for shooting history.

Those prefixes isolate corrected attribution from older history generated under incompatible matchup semantics. Removing or changing a prefix is a learning-data compatibility change, not a cosmetic string change.

Strategic history also depends on which strategies are currently banned/available. `gamePersistence.js` therefore keys strategic/targeting cache variants by matchup plus a stable sorted availability signature so one restricted request cannot reuse a cache entry produced for another availability set.

## Hive Mind learning and OutcomeId flow

1. Unity establishes/uses the connection's shared server `Game` through `setup-level` and receives a `GameId`.
2. Multiple Unity Levels on the same WebSocket intentionally reuse that one Hive Mind `Game`.
3. Targeting, command and shooting requests derive matchup representations and read historical outcome rows/cache variants.
4. The server selects a strategy and creates a temporary positive `OutcomeId`.
5. `outcomeReservations.js` persists reservation metadata under the authenticated user before the response becomes durable protocol state.
6. Unity executes the strategy and accumulates final TSV/outcome, including delayed projectile attribution to the originating command OutcomeId.
7. `store-commands` returns temporary IDs with their scores/discards.
8. BeesServer loads/validates reservation ownership and writes learning rows transactionally.
9. Reservation metadata is deleted only as part of successful commit or explicit terminal discard.
10. Client-visible success is downstream of required durable work.

Database row `ID` and temporary `OutcomeId` are different concepts.

A reservation is not invalid merely because the original WebSocket disconnected, the in-memory Game was retired, or time passed. Reconnect can create a replacement shared Game and still resolve durable reservations by authenticated user ownership.

Mixed stale/valid StoreCommands batches preserve valid writes while reporting stale IDs. Explicit discard is terminal for that OutcomeId and is processed before unrelated sibling failures can strand it.

## Profile/user-data flow

Ordinary server-backed data:

1. Unity sends `get-user-data(UserId, DataFile)`.
2. BeesServer reads the newest row for `(userId, filename)`.
3. A missing row is valid first-run state; a database/authentication failure is not missing data.
4. Unity may create/store a default payload for a genuinely missing logical file.
5. Ordinary writes update existing logical records; shared template behavior can insert versioned rows where defined.

Campaign/challenge shared level templates use synthetic shared-user behavior and remain read-only to ordinary clients.

### Atomic campaign/profile checkpoint

Unity can send reserved `__campaign_checkpoint__` data containing seven related profile documents. `campaignCheckpoint.js` validates completeness and stores the set through one pinned database transaction, preserving all-or-nothing profile checkpoint semantics. This is distinct from ordinary single-file user-data writes.

## Consolidation

Raw learning rows normally begin with `uses = 1`. Once a matchup/strategy accumulates enough history, the modular persistence layer batches rows, computes exact weighted totals with `BigInt`, deletes source rows and reinserts at most two rows whose integer outcome/uses representation preserves the exact total.

All delete/reinsert work runs through one pinned database transaction. Cache invalidation occurs after commit. Failed batches are requeued/retried rather than silently discarded.

Consolidation coordinates with active/in-flight StoreCommands writers. A disconnected WebSocket does not prove the originating DB transaction has finished.

## Current migration set

`schemaMigrations.js` currently applies idempotent metadata-driven migrations for:

- `stored_user_data(userId, filename, ID)` lookup index;
- `settings(userId, name, version, Id)` lookup index;
- `settings.userId -> BIGINT`;
- all three learning-table `uses -> BIGINT UNSIGNED`.

`migrate.js` defaults to the test database. Production migration requires explicit `BEES_ALLOW_PRODUCTION_MIGRATION=1`; automated qualification must never use production `ram`.

## Important invariants

1. Test/integration startup uses `bees_test`; normal startup uses `ram`.
2. `stored_user_data.ID` is the physical primary key; `(userId, filename)` is the logical file identity.
3. Current migrated `settings.userId` is `BIGINT` and learning-table `uses` columns are `BIGINT UNSIGNED`.
4. Matchup IDs remain exact unsigned 64-bit decimal strings in JavaScript/MySQL boundaries.
5. Steam/user identity is preserved exactly and is distinct from request/Game/Outcome/row identities.
6. Strategy numeric IDs/order are persistent data schema.
7. Temporary `OutcomeId` is not database row `ID`.
8. Pending OutcomeId ownership ends only by successful durable commit or explicit terminal discard.
9. `store-commands` success occurs only after required durable persistence.
10. Settings are an exact name/version contract between Unity and BeesServer.
11. Corrected targeting/shooting key namespaces are learning-history compatibility boundaries.
12. Current Unity version 5 has matching configuration/starting-settings/ship-stats rows in the reference dataset used to seed `bees_test`.

## Remaining schema risks / future work

### Outcome primary-key exhaustion

Outcome-table physical IDs remain `INT UNSIGNED`. Their reference-dump AUTO_INCREMENT counters were already roughly 0.58–0.95 billion despite only about one thousand retained rows because raw training rows are later consolidated/deleted. Plan a deliberate migration to `BIGINT UNSIGNED` before counters approach the 4.29-billion limit.

### Shared template ownership

Campaign/challenge shared templates currently use synthetic-user behavior. A future explicit template/version domain would be clearer than representing templates as player-like rows, but any migration must preserve current Unity lookup semantics.

## Qualification expectations

Live database qualification against migrated `bees_test` verifies, among other things:

- selected database is exactly `bees_test`;
- required tables/columns exist;
- `stored_user_data.ID` is the primary key;
- `settings.userId` and `stored_user_data.userId` are `BIGINT`;
- outcome `matchup_id` columns are `BIGINT UNSIGNED`;
- outcome `uses` columns are `BIGINT UNSIGNED`;
- required logical lookup indexes exist;
- observed strategy IDs remain valid for current registries;
- current version-5 settings rows contain required fields;
- reserved test-user writes do not mutate other users;
- real get-strategy/store-commands flow persists/rereads history;
- normal non-test startup continues to target `ram`.
